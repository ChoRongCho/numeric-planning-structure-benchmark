# 13개 플래너 × 휴리스틱 × 6개 도메인 확장 실험

## 1. 목적

이 실험은 단순히 plan을 찾았는지만 비교하지 않는다. 같은 numeric
planning 문제에서 planner와 heuristic의 선택이 다음에 미치는 영향을
측정한다.

- plan 발견 여부와 VAL 유효성
- planning wall-clock time
- 확장된 노드 수
- plan length
- PDDL이 정의한 최소화 목적함수값
- timeout·memory-limit·parser 오류의 구분

최종 목적은 어떤 numeric 구조에서 delete/numeric relaxation이 정보를
잃어 heuristic이 부정확해지는지, 그 부정확성이 탐색량·메모리·plan
품질에 어떻게 나타나는지 분리해 보는 것이다.

## 2. 실험 단위

하나의 case는 다음 조합이다.

```text
planner × heuristic/configuration × domain × problem
```

대상 problem은 6개 domain의 `p000~p004`다.

| 번호 | Domain | PDDL 목적함수 |
| ---: | --- | --- |
| 01 | Blocksworld | `total-cost` |
| 02 | Logistics | `total-delivery-time` |
| 03 | Books | `total-library-time` |
| 04 | Watering | `total-watering-time` |
| 05 | Barman | `total-barman-time` |
| 06 | Assembly | `total-assembly-time` |

이 값들의 이름은 다르지만 모두 `:metric minimize (...)`로 정의되어 있다.
결과 CSV에서는 도메인에 독립적인 `objective_value`라는 공통 이름을
사용한다. 이는 planner 출력을 신뢰해 추출하지 않고 VAL의
`Final value` 결과에서 읽는다.

모든 PDDL이 같은 방향인 minimize를 요청하지만, 13개 configuration이
모두 최적성을 증명하는 것은 아니다. 따라서 `objective_value`는 “최적값”이
아니라 각 configuration이 제한 시간 안에 반환한 valid plan의 결과값이다.

## 3. 휴리스틱 비교 설계

휴리스틱의 효과를 분리하기 위해 각 planner 내에서 search와 부가 option은
고정하고 heuristic만 변경한다. search까지 모두 교차하는 실험은 이
결과를 분석한 후 별도로 수행한다.

| Planner | 고정 search | 비교 heuristic |
| --- | --- | --- |
| ENHSP | WA* | `hadd`, `hmax`, `aibr`, `hradd`, `hrmax`, `hmrp`, `ngc`, `blcost`, `blind` |
| Metric-FF | EHC → weighted best-first | fixed numeric `hFF` |
| Count Downward Agile | lazy greedy | fixed `irhff` |
| PlanForge | A* | `lmcutnumeric`, `blind`, `ff`, numeric PDB/abstraction/cost-partitioning 7종 |
| Patty | JAIR pattern search | state heuristic 없음 |
| Panino | `novbfs_hg` | fixed `hadd` + numeric novelty |
| TamerLite | GBFS, weight 1 | `hadd`, `hff`, `hmax`, explicit/no-number 변형, `blind` 등 8종 |
| Pattint | bounded search | state heuristic 없음 |
| Tempest | EHC → A* fallback | fixed numeric `hFF` |
| OPTIC | EHC → best-first | fixed temporal/numeric RPG |
| OPTIC-Cplex | EHC → best-first | fixed temporal/numeric RPG |
| POPF | EHC → best-first | fixed temporal/numeric RPG |
| Numeric Fast Downward | A* | `lmcutnumeric`, `aibr`, interval/repetition relaxation, numeric PDB 9종 |

총 13개 planner, 45개 configuration이다.

- `p000` 스모크: 45 × 6 = **270 cases**
- `p000~p004` 본 실험: 45 × 6 × 5 = **1,350 cases**

OPTIC에는 `-N`을 주지 않는다. `-N`은 costs를 무시하므로 이번의
목적함수 비교와 맞지 않는다. POPF는 `-n`으로 anytime 최적화를
활성화하고 timeout 전 incumbent를 보존한다.

## 4. 단계별 실행

### 4.1 p000 전 조합 스모크

```bash
./scripts/run/run_changmin_heuristics.sh p000
```

기본 제한은 case당 300초, CPU 2개, process-group RSS 12 GiB, 동시 실행
1개다. terminal에 `현재 case/전체 case`가 계속 출력되며, 같은 내용은
실험 디렉터리의 `terminal.log`에 기록된다.

실행 전 270개 조합만 생성·검사하려면:

```bash
./scripts/run/run_changmin_heuristics.sh p000 --dry-run
```

문제가 있는 configuration만 다시 검증할 때는 filter를 사용한다.

```bash
./scripts/run/run_changmin_heuristics.sh p000 --planner enhsp --heuristic hadd
```

### 4.2 문제별 단계적 확장

`p000` 오류를 수정한 뒤 한 단계씩 늘린다.

```bash
./scripts/run/run_changmin_heuristics.sh p001
./scripts/run/run_changmin_heuristics.sh p002
./scripts/run/run_changmin_heuristics.sh p003
./scripts/run/run_changmin_heuristics.sh p004
```

모두 한 번에 실행하려면:

```bash
./scripts/run/run_changmin_heuristics.sh all
```

자원 제한은 필요할 때 명시적으로 바꿀 수 있다.

```bash
./scripts/run/run_changmin_heuristics.sh p000 \
  --timeout 300 \
  --jobs 1 \
  --cpu-cores 2 \
  --memory-mb 12288
```

## 5. 결과 산출물

각 실험은 다음 형태의 고유 디렉터리를 만든다.

```text
results/raw/changmin-heuristics-<scope>-<timestamp>/
├── configurations.csv
├── results.csv
├── terminal.log
├── manifest.json
└── cases/<planner>/<configuration>/<domain>/<problem>/
    ├── command.json
    ├── planner.log
    ├── plan.val
    ├── validation.log
    ├── resource.txt
    └── result.json
```

`results.csv`의 주요 열은 다음과 같다.

| 열 | 의미 |
| --- | --- |
| `planner` | planner runtime ID |
| `configuration` | heuristic와 고정 search를 포함한 재현 가능 ID |
| `heuristic` | 실행한 heuristic; 없으면 `none` |
| `search` | 고정된 search configuration |
| `benchmark`, `instance` | domain과 problem |
| `status`, `validation` | planner 결과와 VAL 결과 |
| `plan_length` | 추출된 plan action 수 |
| `wall_seconds` | planner process 실행 시간 |
| `expanded_nodes` | planner가 로그에 보고한 expanded node/state 수 |
| `objective_value` | VAL이 계산한 도메인별 최소화 목적함수값 |
| `peak_group_rss_kb` | planner와 자식 process의 최대 합산 RSS |
| `limit_reason` | timeout, memory-limit 등 외부 종료 원인 |
| `plan_path` | 전체 plan 파일 경로 |

planner가 expanded-node counter를 출력하지 않는 경우 `expanded_nodes`는
빈칸으로 남는다. 이를 서로 다른 개념인 evaluated state로 대체하지
않는다.

## 6. p000 통과 기준

`p000`의 목적은 실험 대상과 제외 대상을 분리하는 것이다. 모든
실패를 제외하는 것이 아니다.

| 유형 | 예 | 후속 처리 |
| --- | --- | --- |
| 기술적 비호환 | parser 오류, CLI option 오류, 미지원 numeric effect | 수정 후 재검증. 수정 불가능하면 주 성능 분석에서 제외 |
| 실험 인프라 오류 | plan extractor·metric parser·VAL 연결 오류 | runner를 수정하고 재실행 |
| 성능 결과 | timeout, memory-limit, 진짜 heuristic false dead-end | **제외하지 않고 결과로 기록** |
| 모델링 결함 | 현실에서 불가능한 action, 의도하지 않은 shortcut | domain/problem을 수정하고 전 planner 재검증 |

따라서 p000에서 timeout이나 memory-limit이 나온 configuration도 p001~p004
확장 실험에 남긴다. 그 실패 자체가 planner/heuristic의 구조적 한계다.
반면 parser·표현력 오류는 탐색 성능이 아니므로 주 분석에 섞지 않는다.

### 6.1 plan 의미 검증

VAL은 PDDL 내에서 action이 applicable하고 goal에 도달했는지만 검증한다.
우리가 의도한 로봇 작업인지는 다음과 같이 별도로 분류한다.

| 현상 | 판단 |
| --- | --- |
| 의도상 불가능한 action이 applicable | benchmark action/precondition 결함 |
| 필수 작업을 생략한 shortcut으로 goal 도달 | benchmark goal/invariant 결함 |
| valid action을 사용하지만 불필요한 왕복·적재·하차 반복 | planner의 plan-quality 실패; 실험 결과로 유지 |
| 불필요한 action이 `objective_value`를 증가시키지 않음 | objective/action-cost 모델 결함 |

즉 “왕복이 많다”는 것만으로 benchmark를 고치지 않는다. 왕복이
합법적이고 그 비용이 objective에 반영된다면, 그것은 우리가 측정하려는
비합리적 plan이다. 의도한 제약을 빠져나가는 경로가 있거나 왕복 비용이
목적함수에 빠져 있을 때만 benchmark 문제다.

## 7. 해석 주의점

- `objective_value`는 작을수록 좋지만, timeout에서 얻은 incumbent는
  최적성이 증명된 해가 아닐 수 있다.
- `VAL valid`는 의미 있는 로봇 plan을 보증하지 않는다. plan length와
  objective, 반복 이동을 함께 보아야 한다.
- expanded node의 세부 정의는 planner마다 다를 수 있다. 같은 planner
  내 heuristic 비교가 가장 직접적이며, planner 간 절대값 비교는 주의한다.
- p000은 호환성만 검사한다. 휴리스틱의 열세는 `p001~p004`로 확장해야
  판단할 수 있다.
