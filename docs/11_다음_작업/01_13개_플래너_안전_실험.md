# 13개 플래너 안전 실험

## 목표

`changmin_benchmark`의 6개 domain, p000~p004 총 30개 problem에 대해 13개 planner와
각 planner가 실제로 지원하는 heuristic/search 구성을 조합해 평가한다.
본 실험에서 case 하나의 제한시간은 300초로 고정한다.

첫 실행은 heuristic matrix를 추가하기 전의 13 × 30 = 390 case이다. 모든
case가 timeout까지 간다고 가정하면 순차 실행의 상한은 13시간이다.
heuristic 구성이 평균 H개라면 case 수와 시간 상한은 각각 390H와 13시간 × H가 된다.

maintained `optic`과 local `optic-cplex`를 모두 유지한다. `-N`을 주면 p000과
p001 6개를 모두 풀지만, 이 옵션은 비용과 metric 최적화를 무시한다. 따라서
`-N`은 solvability/호환성 smoke test에만 쓰고 본 최적화 비교에서는 별도
configuration으로 구분한다.

## 현재 장비와 안전 기본값

확인한 장비는 논리 CPU 16개, RAM 약 31 GiB, swap 2 GiB이다. swap은 확인
시점에 거의 사용 중이었으므로, planner를 여러 개 병렬 실행하지 않는다.

`run_changmin_heuristics.sh`의 본 실험에는 다음 제한을 둔다.

```yaml
execution:
  timeout_seconds: 300
  parallel_jobs: 1
  max_cpu_cores: 2
  nice_level: 10
  memory_limit_mb: 12288
  max_processes_per_case: 256
  max_log_size_mb: 64
  monitor_interval_seconds: 0.2
  minimum_available_memory_mb: 14336
```

- 동시에 planner 하나만 실행한다.
- runner와 planner 전체를 논리 CPU 2개에 묶는다.
- CPU 우선순위를 낮춰 데스크톱 응답성을 보존한다.
- planner와 자식 프로세스의 합산 RSS가 12 GiB를 넘으면 해당 case를 종료한다.
- 자식 프로세스 또는 로그가 폭증해도 해당 case만 종료한다.
- 시작 시 가용 RAM이 14 GiB 미만이면 실험을 시작하지 않는다.
- timeout이나 자원 제한으로 한 case가 종료되어도 다음 case는 계속한다.

메모리 제한은 `/proc`를 0.2초마다 확인하는 watchdog이다. 따라서 cgroup의
kernel hard limit처럼 순간적인 초과를 원자적으로 막지는 않는다. 하지만
동시 실행을 하나로 제한하고 case 한도를 12 GiB로 둔다. 또한 시작 시
14 GiB 이상의 가용 RAM을 요구해 planner 한도 외에 최소 2 GiB의 여유를
확보하므로 현재 장비에서 OS까지 함께 죽을 가능성을 낮춘다.

## 결과에서 구분할 상태

- `timeout`: 300초 안에 종료하지 못함
- `memory-limit`: process group 합산 RSS 12 GiB 초과
- `process-limit`: process 수 256개 초과
- `output-limit`: planner 로그 64 MiB 초과
- `unsupported`: domain feature와 planner capability가 맞지 않아 실행하지 않음
- `solved`와 `validation=valid`: 추출한 plan이 VAL 검증을 통과함

`results.csv`의 `max_rss_kb`, `peak_group_rss_kb`, `limit_reason`을 함께 분석해야
단순한 탐색 실패와 시스템 자원 부족을 구분할 수 있다.

## heuristic matrix를 만들 때 지킬 점

planner 이름만 다르고 내부 heuristic이 같은 구성과, 같은 planner에서
heuristic만 바꾼 구성을 구분해 기록한다. 지원하지 않는 옵션을 억지로 넣지
말고 planner별 검증된 configuration ID로 고정한다. 본 실험 전에는 각 구성으로
각 domain의 `p001`만 실행하는 smoke stage를 거친다. smoke stage를 통과한
구성만 24문제 전체로 확장한다.
