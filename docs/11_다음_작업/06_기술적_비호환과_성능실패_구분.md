# 기술적 비호환과 성능 실패의 구분

## 1. 결론

`changmin-heuristics-p000-20260912-145532-288189`의 270개 case를 다시
분류하면 다음과 같다.

| 분류 | case 수 | 주 성능 비교 |
| --- | ---: | --- |
| VAL-valid plan | 237 | 성공으로 포함 |
| parser 비호환 | 4 | N/A로 제외 |
| 특정 heuristic의 numeric-effect 미지원 | 8 | N/A로 제외 |
| false dead-end/false unsolvable | 13 | 실패로 포함 |
| memory-limit | 6 | 실패로 포함 |
| incumbent 없는 timeout | 2 | 실패로 포함 |

따라서 성능 비교의 분모는 `270 - 12 = 258`이다. 이 중 237개가 valid
plan이고, 21개가 실제 planner/heuristic의 탐색·자원·판정 실패다.

위 표는 270개를 중복 없이 나눈 것이다. valid 237개 중 53개는 최초
집계에서 runner의 plan extractor 오류로 `not-extracted`였지만, 원본 로그를
다시 추출해 VAL로 검증하여 모두 valid로 복구했다. 또한 valid 237개 중
2개는 timeout 전에 확보한 incumbent다.

단, 12개 N/A는 연구에서 버리는 데이터가 아니다. **runtime 성능과 plan
품질을 비교할 때만 제외**하고, numeric planning 방법의 입력 표현력 및
적용 범위를 분석하는 표에는 별도로 보고한다.

## 2. benchmark 자체에 문법 문제가 있는가

없다. 현재 여섯 domain과 각 p000을 VAL parser로 다시 검사한 결과 모두

## 3. Patty/Pattint의 4개 parser 비호환

### 대상

| Planner | Blocksworld | Logistics |
| --- | --- | --- |
| Patty | parser 비호환 | parser 비호환 |
| Pattint | parser 비호환 | parser 비호환 |

### 직접 원인 1: `:action-costs` lexical/parser 오류

두 domain의 requirements에 합법적인 `:action-costs`가 들어 있다.

- Blocksworld: `(:requirements :strips :typing :action-costs)`
- Logistics: `(:requirements :strips :fluents :action-costs)`

Patty/Pattint 로그는 각각 이 위치에서 다음 오류를 낸다.

```text
extraneous input ':action' expecting {':', ')'}
```

두 구현의 grammar는 requirement를 `':' NAME`으로 읽도록 되어 있지만,
lexer가 `:action-costs`의 앞부분을 예약 토큰 `:action`으로 먼저 인식한다.
즉, 유효한 requirement 이름을 처리하지 못하는 parser 구현 문제다.

### 직접 원인 2: 명시적 type이 없는 parameter를 처리하지 못함

01·02는 unary predicate로 객체 종류를 표현하는 합법적인 untyped PDDL이다.
예를 들어 `(block ?block)`과 `(package ?package)`를 사용한다. PDDL에서
명시적 type이 없는 parameter는 기본 `object` type이므로 잘못된 문법이
아니다.

그러나 Patty/Pattint grammar의 predicate와 function 정의는 parameter마다
`?x - type`을 요구한다. 그래서 다음 오류가 연쇄적으로 발생한다.

```text
mismatched input ')' expecting '-'
```

Patty의 `TypedPredicate.fromNode()`도 type이 없으면 `paramType=None`인 상태로
`types[paramType]`을 조회한다. parser가 PDDL의 기본 object type을 구현하지
않은 것이다.

### 판정

- benchmark 문제: **아님**
- planner 전체가 numeric planning을 못하는가: **아님**. 같은 Patty/Pattint가
  명시적으로 typed된 Books, Watering, Barman, Assembly는 각각 valid plan을
  만들었다.
- 정확한 분류: **Patty/Pattint parser가 합법적인 requirements/untyped 문법을
  지원하지 않는 것**
- 성능 비교 처리: 4건 모두 `N/A(parser-incompatible)`

## 4. Barman의 numeric-effect 미지원 8건

Barman PDDL 자체는 VAL-valid이며, 같은 planner의 다른 heuristic도 valid
plan을 만든다. 따라서 planner 전체 문제가 아니라 **특정 heuristic
구현이 허용하는 numeric fragment의 한계**다.

### 4.1 NFD `numeric_pdb` 1건

NFD는 Barman을 번역한 뒤 `numeric_pdb`를 구성하면서 종료한다.

```text
ERROR: actions that assign and inc/decrement variables
```

Barman은 합법적인 numeric effect를 다음과 같이 함께 사용한다.

- `assign`: shot의 현재 부피를 dispenser의 토출량으로 설정
- `increase`: shaker 부피와 전체 작업 비용 증가
- `decrease`: dispenser 재고와 shaker 부피 감소

NFD의 `lmcutnumeric`, `irhmax`, `irhadd`, `irhff` 등은 같은 Barman에서
valid plan을 만든다. 따라서 이는 NFD 전체의 실패가 아니라
`numeric_pdb`의 effect-fragment 제한이다.

판정: `N/A(unsupported-numeric-effect)`

### 4.2 PlanForge PDB 2건

대상 heuristic은 다음 둘이다.

- `greedy_numeric_pdb`
- `canonical_numeric_pdb`

오류 메시지는 다음과 같다.

```text
unsupported numeric effects for projected tasks:
mixed assignment and lifted additive effects are not supported
```

여기서 lifted additive effect는 예를 들어 다음과 같이 증가량도 fluent인
효과다.

```lisp
(increase (liquid-volume ?shaker) (liquid-volume ?shot))
```

판정: 2건 모두 `N/A(unsupported-numeric-effect)`

### 4.3 PlanForge domain abstraction/CEGAR 5건

대상 heuristic은 다음 다섯이다.

- `domain_abstraction`
- `canonical_domain_abstractions`
- `multi_domain_abstractions`
- `scp_online`
- `fill_scp`

공통 오류는 다음과 같다.

```text
numeric-fd parity: assignment effects require constant RHS,
got Regular for numeric var 10
```

Barman에는 상수가 아닌 다른 fluent를 우변으로 쓰는 합법적인 assignment가
있다.

```lisp
(assign (liquid-volume ?shot) (dispense-amount ?dispenser))
(assign (liquid-volume ?shot) (container-capacity ?shot))
```

CEGAR 탐색이 느리거나 부정확했던 것이 아니다. 추상 task 생성 단계가 이
effect 형식을 표현하지 못해 **탐색을 시작하지 못했다**.

판정: 5건 모두 `N/A(unsupported-numeric-effect)`

## 5. 제외하면 안 되는 21개 실제 실패

| 원인 | 대상 | case 수 | 이유 |
| --- | --- | ---: | --- |
| false dead-end | ENHSP `aibr`, 전 domain | 6 | parse/ground 후 초기 상태를 잘못 dead end로 판정 |
| false unsolvable | maintained OPTIC, Logistics~Assembly | 5 | 입력을 읽고 RPG/LP 전처리 후 해가 있는 문제를 unreachable로 판정 |
| memory-limit | NFD `aibr` 3건 + `iihmax/iihadd/iihff` Barman | 6 | 실제 heuristic/search 실행 중 RSS 8 GiB 초과 |
| false unsolvable | POPF, Barman·Assembly | 2 | 초기 RPG에서 필요한 action을 제거하고 unsolvable 판정 |
| timeout | POPF Watering | 1 | 120초 탐색 중 incumbent 없음 |
| timeout | TamerLite `hmax_explicit` Barman | 1 | 120초 내 plan 없음 |

이 21건은 parser나 명시적 미지원 오류가 아니다. 다른 configuration이
같은 문제를 푼다는 이유만으로 제외해서도 안 된다. 바로 그 차이가
planner/heuristic의 실제 한계다.

특히 `unsolvable`이라는 출력 문자열만으로 parser 비호환으로 분류하면 안
된다. parse와 preprocessing을 정상 통과한 뒤 잘못된 dead-end 판단을 내린
것도 planner의 알고리즘 결과다.

## 6. timeout이지만 성공인 2건

OPTIC-Cplex와 POPF의 Logistics는 plan을 먼저 찾아 출력한 다음, 더 좋은
해 또는 최적성 증명을 위해 계속 실행하다 120초 제한에 걸렸다. 저장된
incumbent는 VAL-valid다.

따라서 두 case의 기록은 다음 두 사실을 동시에 보존해야 한다.

- coverage: 성공
- anytime/optimization termination: timeout

이를 incumbent 없는 timeout과 같은 실패로 합치면 안 된다.

## 7. runner 문제 53건

PlanForge의 53개 `not-extracted`는 ANSI 색상 escape code 때문에 기존 plan
extractor가 action line을 찾지 못한 문제였다. planner는 정상적으로 plan을
출력했다.

extractor 수정 후 원본 로그를 재처리하고 VAL로 검증한 결과 53/53 valid다.
이는 benchmark 문제도 planner 문제도 아닌 **실험 runner 문제**이며, 이미
수정되었다.

## 8. 앞으로 CSV에 적용할 판정 규칙

| 상황 | 기록 | 성능 분모 |
| --- | --- | --- |
| 독립 parser인 VAL이 거부 | `invalid-benchmark` | 전체 실험 중단 후 benchmark 수정 |
| VAL은 허용하지만 planner parser가 거부 | `parser-incompatible` | 제외(N/A) |
| heuristic이 명시적으로 effect fragment 미지원 보고 | `unsupported-numeric-effect` | 제외(N/A) |
| parse/translation 후 false dead-end/unsolvable | `false-unsolvable` | 실패로 포함 |
| memory-limit 또는 incumbent 없는 timeout | 기존 상태 | 실패로 포함 |
| timeout 전에 VAL-valid incumbent 확보 | `solved` + `limit_reason=timeout` | 성공으로 포함, 최적성 미확인 표시 |
| plan 출력 후 extractor만 실패 | `runner-error` | 수정 후 재추출·검증; planner 실패로 집계 금지 |

성능 표와 별개로 `parser-incompatible` 및 `unsupported-numeric-effect` 표를
반드시 함께 제시한다. 그래야 성능 열세와 입력 표현력 한계를 혼동하지
않는다.
