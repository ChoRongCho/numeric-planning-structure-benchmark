## 5. 휴리스틱별 원인

### 5.1 ENHSP `aibr`

6개 domain 모두에서 초기 heuristic이 `Float.MAX_VALUE`에 해당하는
`3.4028235E38`을 반환하고, 초기 상태를 dead end로 판정했다. 실제로는
모두 해가 있으므로 false dead-end이다.

이는 parser 오류가 아니라 heuristic의 false dead-end이므로 제외하지 않고
실험 결과로 남긴다. ENHSP의 `hadd`, `hmax`, `hradd`, `hrmax`,
`hmrp`, `ngc`, `blcost`, `blind`은 6/6 valid다.

### 5.2 Numeric Fast Downward

| Heuristic | valid | 실패 |
| --- | ---: | --- |
| `lmcutnumeric` | 6/6 | 없음 |
| `irhmax`, `irhadd`, `irhff` | 각 6/6 | 없음 |
| `iihmax`, `iihadd`, `iihff` | 각 5/6 | Barman에서 8 GiB 초과 |
| `aibr` | 3/6 | Logistics·Books·Barman에서 8 GiB 초과 |
| `numeric_pdb` | 5/6 | Barman의 assignment+increase/decrease 혼합 효과 미지원 |

메모리 실패는 단순한 p000에서도 약 9~19초 안에 발생했다.
특히 Barman에서 interval 계열은 heuristic이 0에 도달한 직후 메모리가
약 11 MiB에서 8 GiB 이상으로 증가했다. 문제 크기가 아니라
numeric effect를 처리하는 heuristic/search 구현과의 구조적 충돌이다.

반면 repetition을 모델링하는 `irhmax/irhadd/irhff`는 모두 6/6이고
peak RSS도 약 10 MiB였다. 이 대비를 p001 이상에서 유지해야 한다.

### 5.3 PlanForge의 PDB·domain abstraction

`lmcutnumeric`, `blind`, `ff`는 6/6 valid다. 나머지 7개 heuristic는
Barman에서 모두 초기화 중 crash했다.

- numeric PDB: projected task에서 assignment와 lifted additive effect의 혼합을
  지원하지 않음
- domain abstraction/CEGAR 계열: assignment effect의 우변이 constant가
  아닌 regular numeric variable인 형식을 추상 task로 변환하지 못함

이는 CEGAR가 탐색에서 열세라는 결과가 아니다. **CEGAR
휴리스틱의 입력 표현력 제한**으로 추상화 자체를 만들지 못한
것이다.

### 5.4 OPTIC/POPF

- maintained OPTIC 최적화 mode는 Blocksworld만 valid고 나머지 5개를 즉시
  unreachable/unsolvable로 판정했다.
- OPTIC-Cplex는 6/6 valid plan을 찾었다.
- 하지만 OPTIC-Cplex–Logistics는 `objective_value=3`의 plan을 즉시
  찾고도 120초 동안 최적화를 계속했으며 peak RSS가 약 3.71 GiB였다.
- POPF–Logistics도 같이 valid incumbent를 찾은 후 120초 timeout이었다.
- POPF–Watering은 incumbent 없이 timeout, Barman·Assembly는 unsolvable로
  판정했다.

따라서 CSV의 `status=solved`만 보면 OPTIC-Cplex·POPF의 Logistics
최적화 비용을 놓친다. `limit_reason=timeout`과 incumbent의 VAL 결과를
함께 보아야 한다.

### 5.5 나머지 호환성 문제

- Patty·Pattint: Blocksworld·Logistics의 typing/parser 문제가 재현됐다.
- TamerLite: `hmax_explicit`만 Barman에서 120초 timeout이고 나머지
  47개 case는 valid다.
- Count Downward, Metric-FF, Panino, Tempest는 해당 고정 configuration으로
  6/6 valid다.

## 6. expanded-node 열의 범위

expanded node-node는 로그에 명시적 counter가 있는 planner만 수집됐다.

- 수집 가능: Count Downward, ENHSP, NFD, Panino, PlanForge
- 빈칸: Metric-FF, OPTIC/POPF, Patty/Pattint, TamerLite, Tempest

Metric-FF는 evaluated state만, OPTIC/POPF는 states evaluated만 보고한다. 이것을
expanded node로 잘못 대체하지 않았다. planner 간 node count 비교는 정의가
다르므로 주의하고, 먼저 같은 planner 내 heuristic 비교에 사용한다.

## 7. 확장 전 판정

실험에서 제외할 것은 “못 푸는 configuration”이 아니라 “탐색에
진입하지도 못하는 기술적 비호환”이다.

1. PlanForge extractor 버그는 수정했으며 재실행 시 정상 집계된다.
2. Patty/Pattint의 01·02 parser 문제를 수정하거나, 수정할 수 없으면
   이 조합을 주 성능 분석에서 제외한다.
3. PlanForge PDB·CEGAR와 NFD numeric PDB의 Barman 실패는 메모리/시간
   열세가 아닌 미지원 numeric effect다. 표현력 제한으로 별도 집계한다.
4. ENHSP `aibr`의 false dead-end, NFD AIBR/IIH의 memory-limit, TamerLite의
   timeout, OPTIC/POPF의 탐색 실패는 **제외하지 않는다.** 이것이
   우리가 찾으려는 planner/heuristic의 한계다.
5. 모든 domain에 대해 intended invariant·필수 action·action cost를 검사해,
   valid이지만 의도하지 않은 shortcut이 있는 benchmark는 먼저 수정한다.
6. 합법적인 action을 불필요하게 반복해 objective가 나빠지는 plan은
   benchmark 오류가 아니라 plan-quality 결과로 그대로 유지한다.

### 7.1 목적함수 사전 감사에서 발견한 사항

6개 domain의 action이 공통 `objective_value`에 비용을 추가하는지 검사했다.

- Blocksworld, Books, Watering, Barman, Assembly: 모든 action이 목적함수를
  증가시킨다.
- Logistics: 실험 당시에는 `load-truck`, `unload-truck`의 목적함수
  비용만 0이었다.

Logistics의 0-cost 적재·하차는 이전 모델링 결정이지만, `total-delivery-time`
하나만 보면 불필요한 load/unload 반복을 벌점 없이 허용한다. 따라서
다음 중 하나를 실험 전에 명확히 선택해야 한다.

1. load/unload에 작은 양의 시간을 부여해 모든 불필요 action을
   `objective_value`에서 벌점한다.
2. 0-cost 설계를 유지하되 `plan_length`, load 횟수, unload 횟수,
   반복 상태를 필수 보조 품질 지표로 사용한다.

이 분석 후 `load-truck`과 `unload-truck`에 각각 고정 시간 1을
부여했다. 따라서 수정 후 Logistics에서는 모든 action이
`total-delivery-time`을 증가시킨다. 원시 p000 결과의 Logistics
`objective_value=3`은 수정 전 domain의 값이므로, 수정 후 실험과 직접
비교하지 않는다.
