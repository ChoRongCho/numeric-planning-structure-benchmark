# 실험 구현과 계측 요건

- 작성일: 2026-09-07
- 범위: sequential classical numeric planning
- 1차 대상: capacity와 package weight를 갖는 Capacitated Transport
- 1차 목표: 기존 numeric heuristic의 failure mode를 재현하고 측정하는 실험 기반 구축
- 비목표: 자연어→PDDL 생성, end-to-end LLM planning, temporal/continuous planning

이 문서는 `asset/03_Paper`의 numeric planning 문서들을 바탕으로, 현재 연구에서
실제로 준비하거나 구현해야 할 항목을 체크리스트로 바꾼 것이다.

## 0. 가장 먼저 결정할 것

### 0.1 구현 전략

- [ ] 1차 실험에서는 완전한 numeric planner를 새로 구현하지 않는다.
- [ ] ENHSP를 canonical numeric transition/search substrate로 사용한다.
- [ ] Python runner가 ENHSP 실행, timeout, 로그 수집, 결과 정규화를 담당한다.
- [ ] ENHSP 내부 heuristic 값과 search trace를 얻을 수 있는지 확인한다.
- [ ] 필요한 계측을 CLI 옵션, log parser, source patch 중 어느 방식으로 넣을지 결정한다.
- [ ] ENHSP 내부 접근이 어려우면 작은 분석용 Python search engine을 별도로 만든다.
- [ ] Python engine은 연구용 state-ranking 분석에만 사용하고 ENHSP 결과와 교차 검증한다.
- [ ] planner의 원본 버전, commit hash, Java 버전과 실행 옵션을 고정한다.
- [ ] planner binary/JAR 자체를 저장할지 설치 스크립트만 저장할지 결정한다.
- [ ] 외부 planner 라이선스와 재배포 가능 여부를 기록한다.

### 0.2 1차 지원 범위

- [ ] Sequential action만 지원한다.
- [ ] Boolean proposition과 numeric fluent가 함께 있는 state를 지원한다.
- [ ] Typed object를 지원한다.
- [ ] Numeric comparison `<=`, `<`, `=`, `>=`, `>` 중 실제 필요한 연산자를 확정한다.
- [ ] Numeric effect `assign`, `increase`, `decrease`를 지원한다.
- [ ] 처음에는 linear/constant numeric effect로 제한한다.
- [ ] 처음에는 unit action cost 또는 명시적 action cost 하나만 사용한다.
- [ ] Conditional effect의 포함 여부를 명시한다.
- [ ] Negative precondition의 포함 여부를 명시한다.
- [ ] Disjunctive precondition은 1차 범위에서 제외할지 명시한다.
- [ ] Derived predicate는 1차 범위에서 제외할지 명시한다.
- [ ] Nonlinear expression은 후속 단계로 둔다.
- [ ] State-dependent effect는 후속 coupling 실험에서만 추가한다.
- [ ] Durative action, continuous process, temporal deadline은 1차 범위에서 제외한다.
- [ ] 지원하지 않는 PDDL construct가 입력되면 조용히 무시하지 않고 실패시킨다.

### 0.3 연구 목표의 경계

- [ ] Exact transition checking과 approximate heuristic guidance를 분리한다.
- [ ] Applicability와 plan validity는 항상 classical planner가 결정한다.
- [ ] Heuristic은 state/action 순서만 바꾸도록 한다.
- [ ] Hard pruning은 1차 실험에서 사용하지 않는다.
- [ ] Satisficing coverage와 optimal plan cost를 같은 주장으로 섞지 않는다.
- [ ] 1차 연구에서는 coverage, search effort, runtime을 주 목표로 둔다.
- [ ] Optimality/admissibility 연구는 별도 트랙으로 표시한다.

## 1. PDDL 입력과 문제 모델

### 1.1 Domain parser/loader

- [ ] Domain 이름을 읽는다.
- [ ] PDDL requirements 선언을 읽고 지원 여부를 검사한다.
- [ ] Type hierarchy를 읽는다.
- [ ] Predicate schema를 읽는다.
- [ ] Numeric function/fluent schema를 읽는다.
- [ ] Action schema와 typed parameter를 읽는다.
- [ ] Positive/negative Boolean precondition을 구분한다.
- [ ] Numeric precondition의 좌변, 우변, 비교 연산자를 보존한다.
- [ ] Boolean add/delete effect를 구분한다.
- [ ] Numeric assignment/increase/decrease effect를 구분한다.
- [ ] Action cost expression을 별도로 식별한다.
- [ ] Static predicate와 dynamic predicate를 구분한다.
- [ ] Static numeric constant와 dynamic fluent를 구분한다.
- [ ] 파싱 오류에 파일명, 줄 또는 construct 정보를 포함한다.

### 1.2 Problem parser/loader

- [ ] Problem 이름과 연결된 domain 이름을 읽는다.
- [ ] Typed object 목록을 읽는다.
- [ ] Initial Boolean facts를 읽는다.
- [ ] Initial numeric fluent 값을 읽는다.
- [ ] Boolean goal condition을 읽는다.
- [ ] Numeric goal condition을 읽는다.
- [ ] Metric minimize expression을 읽는다.
- [ ] 선언되지 않은 object/predicate/function 참조를 검사한다.
- [ ] 초기값이 없는 numeric fluent의 처리 정책을 명시한다.
- [ ] 중복 initial fact/value를 탐지한다.
- [ ] 음수, 0, 실수 weight/capacity의 허용 범위를 명시한다.

### 1.3 내부 표현

- [ ] Boolean state를 compact set 또는 bit vector로 표현한다.
- [ ] Numeric state를 고정 순서 vector와 fluent index map으로 표현한다.
- [ ] State를 `<Boolean facts, numeric vector>`로 명시적으로 구분한다.
- [ ] Ground action에 Boolean/numeric precondition을 모두 보관한다.
- [ ] Ground action에 Boolean/numeric effect를 모두 보관한다.
- [ ] Object identity와 type을 보존한다.
- [ ] Package weight처럼 정적인 numeric 값도 object와 연결해 조회 가능하게 한다.
- [ ] Capacity, current load, remaining resource의 의미를 구분한다.
- [ ] Goal test가 mixed Boolean/numeric conjunction을 처리한다.
- [ ] Action cost와 execution-time metric을 혼동하지 않는다.

### 1.4 Numeric expression 처리

- [ ] 상수식을 평가한다.
- [ ] Fluent reference를 현재 state에서 조회한다.
- [ ] 덧셈과 뺄셈을 평가한다.
- [ ] 허용 범위에서 곱셈/나눗셈을 평가한다.
- [ ] 비교식의 tolerance 정책을 정의한다.
- [ ] Integer-valued benchmark에서는 exact integer arithmetic 사용 가능성을 검토한다.
- [ ] Float를 사용할 경우 state hashing용 canonicalization을 정의한다.
- [ ] NaN, infinity, division-by-zero를 명시적으로 거부한다.
- [ ] 서로 다른 단위(kg, distance, energy)를 섞지 않도록 metadata를 둘지 결정한다.
- [ ] Numeric expression을 AST 또는 normalized linear form으로 보존한다.

## 3. 정확한 transition engine

### 3.1 Applicability

- [ ] 모든 Boolean precondition을 검사한다.
- [ ] 모든 numeric precondition을 현재 값으로 정확히 평가한다.
- [ ] Capacity 초과 pickup을 successor 생성 전에 차단한다.
- [ ] 서로 다른 numeric condition의 conjunction을 모두 만족해야 한다.
- [ ] Equality/tolerance edge case를 테스트한다.
- [ ] Action applicability 실패 원인을 debug mode에서 기록할 수 있게 한다.

### 3.2 Successor 생성

- [ ] Boolean add/delete effect를 적용한다.
- [ ] Numeric assign/increase/decrease effect를 적용한다.
- [ ] 동일 action의 여러 numeric effect가 적용되는 의미론을 확인한다.
- [ ] Effect 우변이 pre-state를 읽는지 PDDL 의미론에 맞춘다.
- [ ] Source state를 mutate하지 않고 successor를 생성한다.
- [ ] Numeric invariant 위반 successor를 탐지한다.
- [ ] 각 transition에 action cost를 누적한다.
- [ ] Parent/action pointer로 plan을 복원한다.

### 3.3 State identity와 duplicate handling

- [ ] Boolean fact set을 안정적으로 hash한다.
- [ ] Numeric vector를 안정적으로 hash한다.
- [ ] Float canonicalization 때문에 다른 state가 합쳐지지 않는지 검사한다.
- [ ] 같은 state에 더 낮은 `g`로 도달했을 때 reopen 정책을 정의한다.
- [ ] Generated, unique, duplicate state 수를 따로 센다.
- [ ] Closed-list memory 사용량을 측정한다.

### 3.4 Goal과 plan 검증

- [ ] Boolean goal을 최종 state에서 검사한다.
- [ ] Numeric goal을 최종 state에서 검사한다.
- [ ] 반환 plan을 initial state부터 독립적으로 replay한다.
- [ ] 각 step의 applicability를 재검사한다.
- [ ] 각 step의 numeric state trace를 선택적으로 저장한다.
- [ ] 최종 plan cost를 재계산한다.
- [ ] Invalid plan은 solved로 집계하지 않는다.
- [ ] 외부 validator 사용 가능 여부를 확인한다.
- [ ] Planner의 reported cost와 validator cost를 비교한다.

### 4.1 최소 search algorithm

- [ ] Greedy Best-First Search를 제공한다.
- [ ] Weighted A*를 선택적으로 제공한다.
- [ ] Optimal 분석용 A*/UCS를 작은 instance에 제공한다.
- [ ] 동일 heuristic 비교에서 search algorithm을 고정한다.
- [ ] Open-list ordering key를 기록한다.
- [ ] Tie-breaking 규칙을 고정하고 기록한다.

- [ ] Goal-on-generation과 goal-on-expansion 중 정책을 기록한다.

### 4.2 자원 제한과 종료

- [ ] CPU time도 필요하면 별도로 기록한다.

- [ ] Multi-queue를 사용할 때 queue scheduling을 기록한다.
- [ ] Novelty queue를 선택적으로 추가할 수 있게 한다.
- [ ] 모든 applicable action을 남기는 fallback queue를 지원할 수 있게 한다.

## 9. Controlled Capacitated Transport benchmark

### 9.1 최소 domain 요소

- [ ] Carrier 1개.
- [ ] Capacity fluent 또는 static numeric function.
- [ ] Current-load fluent.
- [ ] Package별 weight.
- [ ] Package 위치와 carrier 위치.
- [ ] `pickup` action.
- [ ] `deliver` 또는 `unload` action.
- [ ] 필요하면 `move`와 `return` action.
- [ ] 모든 package delivery goal.
- [ ] 1차에는 battery와 deadline을 제외한다.

### 9.2 축 A: 일반 problem size

- [ ] Package 수: 예를 들어 5, 10, 20, 40, 80.
- [ ] Location 수 변화 여부를 별도 parameter로 둔다.
- [ ] Vehicle 수는 1차에 고정한다.
- [ ] Numeric constraint 구조는 동일하게 유지한다.
- [ ] Ground action 수와 goal 수를 함께 기록한다.

### 9.3 축 B: Numeric dimensionality

- [ ] Level 1: capacity + weight.
- [ ] Level 2: capacity + weight + battery.
- [ ] Level 3: capacity + weight + battery + deadline.
- [ ] Object 수와 topology는 level 사이에서 통제한다.
- [ ] 단순 fluent 추가와 실제 dependency 추가를 구분한다.

### 9.4 축 C: Coupling strength

- [ ] Independent: energy가 load와 무관.
- [ ] Weak: energy가 distance에만 의존.
- [ ] Strong: energy가 distance와 current load에 의존.
- [ ] 한 action이 읽는 fluent 수를 조절한다.
- [ ] 한 action이 변경하는 fluent 수를 조절한다.
- [ ] 같은 resource를 공유하는 object 수를 조절한다.
- [ ] Coupling score를 정량화하는 proxy를 정의한다.

### 9.5 축 D: Capacity tightness

- [ ] Loose: 여러 grouping이 모두 feasible.
- [ ] Medium: 일부 grouping 선택이 필요.
- [ ] Tight: 잘못된 grouping이 추가 trip을 유발.
- [ ] Adversarial: greedy pickup이 미래 batch를 깨뜨림.
- [ ] Tightness를 단순 capacity ratio와 packing slack 두 방식으로 기록한다.
- [ ] 동일 package 수에서 tightness만 변경한다.

### 9.6 축 E: Goal/resource sharing

- [ ] Independent goals: 각 goal이 별도 resource 사용.
- [ ] Shared capacity: 여러 goal이 carrier 하나를 공유.
- [ ] Multiple shared resources: capacity와 battery를 동시에 공유.
- [ ] Goal 수는 고정한 채 sharing 구조만 변경한다.

### 9.7 핵심 instance family

- [ ] 동일 총무게, 다른 package distribution.
- [ ] `[7, 5, 6, 6]` 계열.
- [ ] `[8, 8, 4, 4]` 계열.
- [ ] Capacity 12, `[7, 5, 6, 6, 4, 4, 3]` adversarial 계열.
- [ ] Perfect-pair가 많은 instance.
- [ ] Perfect-pair가 거의 없는 instance.
- [ ] One-heavy-many-light instance.
- [ ] 균일 weight instance.
- [ ] Greedy first-fit이 optimal한 instance.
- [ ] Greedy first-fit이 suboptimal한 instance.
- [ ] 같은 lower bound지만 optimal trip 수가 다른 instance.
- [ ] 좋은 partial batch와 나쁜 partial batch가 명확한 state pair.

### 9.8 Generator 요구사항

- [ ] 모든 generator에 random seed를 받는다.
- [ ] Parameter를 CLI/config로 지정한다.
- [ ] 생성 instance가 최소 하나의 plan을 갖도록 보장하거나 검증한다.
- [ ] 의도한 tightness/coupling level을 manifest에 기록한다.
- [ ] 실제 계산된 통계도 manifest에 기록한다.
- [ ] 중복 instance를 탐지한다.
- [ ] Stable filename 규칙을 사용한다.
- [ ] Generator version을 결과에 기록한다.
- [ ] Train/validation/test split을 생성 시점에 고정한다.
- [ ] Test에는 training보다 큰 object 수/OOD distribution을 포함한다.
- [ ] 사람 검사용 tiny instance를 별도로 둔다.
- [ ] PDDL syntax 검사를 자동화한다.

## 10. Ablation matrix

- [ ] Numeric value는 유지하고 object relation을 단순화한다.
- [ ] Object 수는 유지하고 capacity constraint를 제거한다.
- [ ] Fluent 수는 유지하고 fluent dependency를 제거한다.
- [ ] 동일 총무게에서 weight distribution만 변경한다.
- [ ] 동일 shortest-path distance에서 load-dependent effect만 제거한다.
- [ ] Shared resource를 independent resource로 바꾼다.
- [ ] Resource consumption effect를 제거한다.
- [ ] Resource replenishment action을 제거/추가한다.
- [ ] Package/object 이름을 익명화한다.
- [ ] Predicate/function 이름을 의미 없는 token으로 바꾼다.
- [ ] Weight 값을 object 사이에서 permutation한다.
- [ ] Capacity 값만 변경한다.
- [ ] Generated heuristic에서 numeric term만 제거한다.
- [ ] Handcrafted heuristic에서 grouping term만 제거한다.
- [ ] Helpful action guidance만 켜고 heuristic score는 고정한다.
- [ ] Heuristic score만 사용하고 helpful action은 끈다.
- [ ] Single queue와 multi-queue를 비교한다.
- [ ] Fallback queue 유무를 비교한다.

## 23. 핵심 결론

이 연구에 필요한 최소 시스템은 단순히 PDDL을 받아 plan을 출력하는 planner가
아니다. 아래 네 부분이 모두 있어야 현재 가설을 검증할 수 있다.

1. 정확한 numeric transition과 plan validation을 제공하는 ENHSP 기반 실행층
2. 여러 classical heuristic을 같은 search 조건에서 비교하는 baseline 층
3. `h(s)`와 true remaining cost, ranking, plateau를 관측하는 계측/oracle 층
4. size, tightness, coupling과 grouping을 독립적으로 조절하는 benchmark 층

특히 3번이 없으면 “planner가 timeout 났다”까지만 말할 수 있고, heuristic이
resource interaction을 잃어서 실패했다는 연구 가설은 검증할 수 없다.
