# 13개 플래너 다운로드와 설치

이 문서는 이 저장소를 다른 Ubuntu 컴퓨터로 옮긴 뒤, 현재 실험에 사용하는 13개
planner ID를 다시 실행하기 위한 매뉴얼이다.

## 1. 가장 중요한 결론

현재 `planners/`는 약 3.8 GiB이며 Git에는 포함하지 않는다. 벤치마크와 실험 코드는
Git으로 받고, 플래너 실행 환경은 별도 압축 파일로 옮기는 것이 현재 실험을 가장
정확하게 재현하는 방법이다.

이유는 다음과 같다.

- `optic-cplex`와 `popf`는 사용자가 직접 확보한 Linux binary다.
- `numeric-fast-downward-local`에는 upstream에 없는 로컬 수정이 있다.
- 현재 Metric-FF에도 parser/build 호환 수정이 들어가 있다.
- Python, Java, Rust, C++ 및 solver library 버전이 섞여 있어 새 컴퓨터에서 전부
  다시 빌드하면 현재 binary와 달라질 수 있다.
- CPLEX 관련 파일은 라이선스 조건을 확인하지 않고 공개 저장소에 재배포하면 안 된다.

따라서 목적에 따라 아래 두 경로를 구분한다.

| 목적 | 권장 경로 | 재현 수준 |
|---|---|---|
| 같은 연구자가 다른 컴퓨터에서 동일 실험 실행 | A. 현재 실행 번들 이전 | 가장 높음 |
| 공개 source로 환경을 처음부터 재구축 | B. source 재빌드 | 빌드 차이가 생길 수 있음 |

## 3. A안: 현재 실행 환경을 그대로 옮기기

### 3.1 기존 컴퓨터에서 번들 생성

프로젝트 루트에서 실행한다.

```bash
tar --zstd -cf numeric-planners-linux-x86_64-20260914.tar.zst \
  planners/external \
  planners/runtime \
  planners/local \
  planners/deps \
  planners/locks \
  planners/plannerctl \
  planners/capabilities.json \
  planners/README.md

sha256sum numeric-planners-linux-x86_64-20260914.tar.zst \
  > numeric-planners-linux-x86_64-20260914.tar.zst.sha256
```

업로드 서비스의 파일 크기 제한에 걸리면 다음처럼 분할한다.

```bash
split -b 1900M -d -a 2 \
  numeric-planners-linux-x86_64-20260914.tar.zst \
  numeric-planners-linux-x86_64-20260914.tar.zst.part-
```

이 파일은 개인 Google Drive, 연구실 NAS, SSH/SCP 등 허가된 저장소로 옮긴다.
`optic-cplex`가 포함되므로 공개 배포 전에는 반드시 해당 binary의 배포 조건을
확인한다.

### 3.2 새 컴퓨터에서 설치

먼저 Git 저장소를 clone하고 프로젝트 루트로 이동한다. 분할했다면 결합한 뒤 압축을
푼다.

```bash
cat numeric-planners-linux-x86_64-20260914.tar.zst.part-* \
  > numeric-planners-linux-x86_64-20260914.tar.zst

sha256sum -c numeric-planners-linux-x86_64-20260914.tar.zst.sha256
tar --zstd -xf numeric-planners-linux-x86_64-20260914.tar.zst

chmod +x planners/plannerctl planners/local/optic-cplex planners/local/popf
```

분할하지 않았다면 `cat` 단계만 생략한다. 이 archive는 반드시 프로젝트 루트에서
해제해야 `plannerctl`이 기대하는 상대 경로와 일치한다.

### 3.3 Ubuntu 실행 dependency

현재 binary bundle을 만든 환경은 **Ubuntu 22.04 x86-64, Python 3.10, OpenJDK
17, glibc 2.35**다. Python runtime에 `cpython-310-x86_64` native module이 포함되므로
다른 Python minor version을 기본 `python3`로 사용하는 OS는 exact reproduction이
아니다. 가장 안전한 대상도 Ubuntu 22.04 x86-64다.

POPF는 32-bit static binary라 64-bit Ubuntu에서도 실행될 수 있지만, host 보안
정책이나 architecture가 다르면 실행이 차단될 수 있다.

```bash
sudo apt update
sudo apt install -y \
  python3 python3-venv python3-pip \
  openjdk-17-jre-headless \
  libgsl27 libbz2-1.0 zlib1g \
  coinor-libcbc3 coinor-libclp1 coinor-libcoinutils3v5 coinor-libosi1v5
```

Ubuntu release에 따라 COIN-OR runtime package의 숫자 suffix가 다를 수 있다. 그때는
`apt search coinor-libclp`로 해당 release의 이름을 확인한다.

버전을 확인한다.

```bash
python3 --version
java -version
ldd --version | head -1
```

번들 내부 OPTIC은 원래 컴퓨터의 절대 RUNPATH를 포함할 수 있다. 저장소의
`plannerctl`은 실행 시 `planners/deps/local/lib`를 `LD_LIBRARY_PATH`에 자동으로
추가하도록 되어 있으므로 OPTIC binary를 직접 호출하지 말고 `plannerctl`을 사용한다.

### 3.4 설치 확인

```bash
for planner_id in \
  enhsp metric-ff-cross-v1 count-downward-agile planforge-ipc2026 \
  patty-ipc2026-agile-1 panino-lnp-agile \
  tamerlite-ipc2026-agile-1 pattint-bitwuzla \
  tempest-numeric-ipc2026 optic optic-cplex popf-static-v2 \
  numeric-fast-downward-local
do
  planners/plannerctl status "$planner_id"
done
```

모두 `staged`이거나 실행 검증으로 기록된 상태여야 한다. `missing`이면 archive를 잘못된
위치에서 해제했거나 일부 디렉터리가 누락된 것이다. `not-executable`이면 실행 권한을
확인한다.

전체 p000 smoke test는 다음 순서로 수행한다.

```bash
scripts/run/run_changmin_heuristics.sh p000
```

여기서 timeout이나 memory-limit은 planner 성능 결과가 될 수 있지만, `missing`, loader
error, Python import error, Java class error는 설치 실패다.

## 4. B안: 공개 source에서 재구축하기

### 4.1 권장 환경

- host에 직접 설치한다면 Ubuntu 22.04 x86-64
- 각 IPC `Recipe`로 container를 만든다면 Recipe에 적힌 Ubuntu 24.04 등 원래 base
  image를 그대로 사용
- 여유 저장 공간 최소 15 GiB
- RAM 16 GiB 이상 권장
- Python 3.10
- ENHSP runtime은 OpenJDK 17, Panino build는 OpenJDK 21
- CMake/Ninja, GCC/G++, Flex/Bison
- Rust stable

```bash
sudo apt update
sudo apt install -y \
  git build-essential cmake ninja-build pkg-config \
  flex bison unzip curl ca-certificates \
  python3 python3-venv python3-pip \
  openjdk-17-jdk openjdk-21-jdk \
  zlib1g-dev libbz2-dev libgsl-dev \
  coinor-libcbc-dev coinor-libclp-dev \
  coinor-libcoinutils-dev coinor-libosi-dev

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs \
  | sh -s -- -y --profile minimal
```

새 shell을 열거나 아래를 실행해 Cargo를 PATH에 넣는다.

```bash
. "$HOME/.cargo/env"
```

### 4.3 planner별 build

#### ENHSP

```bash
cd planners/external/enhsp
./compile
cd ../../..

mkdir -p planners/runtime/enhsp/bin
cp planners/external/enhsp/enhsp-dist/enhsp.jar \
  planners/runtime/enhsp/bin/enhsp.jar
cp -R planners/external/enhsp/enhsp-dist/libs \
  planners/runtime/enhsp/bin/
```

#### Metric-FF

```bash
make -C planners/external/metric-ff-crossplatform/v1.0
cp planners/external/metric-ff-crossplatform/v1.0/ff \
  planners/external/metric-ff-crossplatform/ff-v1.0
chmod +x planners/external/metric-ff-crossplatform/ff-v1.0
```

현재 실험 binary는 최신 Flex/Bison에 맞춘 parser/build 수정본이다. upstream checkout의
빌드 또는 parsing 결과가 다르면 A안의 binary를 사용해야 동일 실험이 된다.

#### Count Downward

```bash
cd planners/external/count-downward-ipc2026
python3 build.py release64 -j2
cd ../../..
```

#### PlanForge와 Tempest Numeric

```bash
cargo build --release --manifest-path \
  planners/external/planforge-ipc2026/Cargo.toml

cargo build --release --locked --bin planner --manifest-path \
  planners/external/tempest-numeric-ipc2026/Cargo.toml
```

#### Panino

```bash
cd planners/external/panino-ipc2026/src/jpddlplus-private
./compile.sh
cd ../../../..
```

`plannerctl`은 생성된 `jpddlplus.jar`를 직접 실행한다.

#### TamerLite

TamerLite는 Python package와 Rust extension을 함께 사용한다. IPC repository의
`Recipe`가 기준 설치 사양이다. host에 설치할 때는 별도 venv 또는 현재 프로젝트가
사용하는 `planners/runtime/tamerlite/site-packages` 경로를 사용한다. 가장 덜 깨지는
방법은 Recipe대로 Apptainer image를 먼저 빌드해 독립 실행을 확인한 뒤, A안 runtime을
옮기는 것이다.

```bash
sudo apt install -y apptainer
cd planners/external/tamerlite-ipc2026
sudo apptainer build planner.sif Recipe
cd ../../..
```

#### PATTY와 PATTINT

두 planner는 Python/SMT dependency에 민감하다. 각 repository의 `Recipe`가 공식 설치
명세이며, 현재 `plannerctl` 경로와 완전히 맞추려면 A안의 `runtime/`을 사용하는 것이
안전하다.

```bash
cd planners/external/patty-ipc2026
sudo apptainer build planner.sif Recipe
cd ../pattint-ipc2026
sudo apptainer build planner.sif Recipe
cd ../../..
```

PATTINT의 핵심 host dependency는 다음과 같다.

```bash
python3 -m pip install \
  'pysmt>=0.9.5' 'antlr4-python3-runtime==4.12.0' \
  'sympy>=1.5' 'bitwuzla>=0.9.0'
```

#### OPTIC-CLP

```bash
cmake -S planners/external/optic-maintained \
  -B planners/external/optic-maintained/build \
  -GNinja -DCMAKE_BUILD_TYPE=Release
cmake --build planners/external/optic-maintained/build -j2
```

생성 파일은
`planners/external/optic-maintained/build/src/optic/optic-clp`이어야 한다.

#### VAL

실험 runner는 다음 두 파일을 사용한다.

```text
planners/external/dino/src/VAL-master/parser
planners/external/dino/src/VAL-master/validate
```

두 파일이 clone에 포함되지 않거나 실행 파일이 아니면 DiNo 내부 VAL source를 build한
뒤 위 경로에 생성해야 한다. 확인 명령은 다음과 같다.

```bash
test -x planners/external/dino/src/VAL-master/parser
test -x planners/external/dino/src/VAL-master/validate
```

### 4.4 공개 source만으로 대체할 수 없는 세 항목

#### OPTIC-Cplex

현재 파일은 x86-64 static binary다. 새 컴퓨터의 다음 위치로 직접 복사한다.

```text
planners/local/optic-cplex
```

현재 기준 SHA-256은 다음과 같다.

```text
596716381fd9f54da99733a869c9fa42ab67bbbcdc50012eab42800c99960ddd
```

CPLEX를 새로 설치해 source에서 빌드하는 경우에는 IBM license와 설치 경로가 필요하며,
현재 binary와 동일한 build라고 볼 수 없다.

#### POPF Release 2

현재 파일은 32-bit i386 static binary다. 다음 위치로 직접 복사한다.

```text
planners/local/popf
```

현재 기준 SHA-256은 다음과 같다.

```text
b38de24bf3450c91d1e797d7bd5b2f1f633e73fcb7a8e9b563729d2534a02cb3
```

#### Numeric Fast Downward local

현재 실험본의 upstream은 아래와 같지만, 두 core 파일과 연구용 보조 파일에 로컬 변경이
있다.

```text
URL: https://github.com/dgnad/numeric-fast-downward.git
revision: 52e5864fa31a5e23addbad77ce068e96ef9e6f71
```

따라서 exact reproduction에는 `planners/local/numeric-fast-downward/` 전체를 옮긴다.
upstream에서 새로 받은 버전은 별도의 planner variant로 취급해야 한다.

## 5. 설치 완료 판정

설치는 단순히 `staged`가 뜨는 것으로 끝나지 않는다. 다음 네 조건을 모두 만족해야
한다.

1. 13개 ID의 `plannerctl status`가 `missing` 또는 `not-executable`이 아니다.
2. p000에서 planner process가 시작되고 parser/import/loader 오류가 없다.
3. 생성된 plan을 동일 VAL binary가 검증한다.
4. 실험 CSV에서 기술적 비호환과 timeout/memory-limit을 구분할 수 있다.

전체 실험은 설치 검증 후에만 실행한다.

```bash
scripts/run/run_changmin_heuristics.sh all
```

현재 자원 설정은 timeout 300초, process당 CPU 2개, memory 12 GiB다. 새 컴퓨터에서
조건을 바꾸면 기존 결과와 같은 표에 섞지 말고 별도 experiment run으로 기록한다.

## 6. Git에 넣는 것과 넣지 않는 것

| Git에 포함 | Git에서 제외 |
|---|---|
| `planners/plannerctl` | `planners/external/` |
| `planners/capabilities.json` | `planners/runtime/` |
| `planners/locks/` | `planners/local/` |
| 설치 문서와 실험 스크립트 | build, dependency, toolchain, download log |

즉 Git 저장소는 실험 정의와 adapter를 보존하고, 별도 planner bundle은 실행 artifact를
보존한다. 이 구분이 현재 저장소의 재현 전략이다.
